# بسته بررسی مستقل برای مدل AI

## هدف این فایل

این فایل برای ارسال به یک مدل هوش مصنوعی مستقل تهیه شده است تا پروژه `Pargar Support Copilot` را از نظر معماری، تجربه کاربری، صحت داده، امنیت، آمادگی عملیاتی و اولویت‌های توسعه بررسی کند.

مدل بررسی‌کننده باید میان این چهار وضعیت تفاوت بگذارد:

1. قابلیت واقعاً پیاده‌سازی‌شده و قابل مشاهده در کد
2. قابلیت پیاده‌سازی‌شده اما محدود به محیط محلی یا Read-Only
3. قابلیت مستندشده اما ناقص، آزمایشی یا دارای مغایرت با کد
4. قابلیت آینده یا صرفاً پیشنهادی

از مدل بررسی‌کننده خواسته می‌شود در نبود شواهد، حدس نزند و هر ادعا را با مسیر فایل، تابع، Endpoint یا تست مربوط پشتیبانی کند.

تاریخ تهیه این بسته: ۵ سپتامبر ۲۰۲۶

## ۱. خلاصه مدیریتی

`Pargar Support Copilot` یک Web Application محلی برای کمک به کارشناسان Helpdesk است. CRM سازمانی Microsoft Dynamics CRM/Dataverse منبع اصلی داده است. برنامه در وضعیت فعلی:

- داده‌های Case، Note، Task، Post و Knowledge Base را با REST API و Windows Integrated Authentication می‌خواند.
- داده‌ها را در Snapshot داخلی SQLite ذخیره می‌کند.
- موارد را از View انتخاب‌شده CRM واکشی می‌کند.
- برای هر مورد، اطلاعات اصلی، فعالیت‌های مرتبط، کمبودهای اطلاعاتی، مقالات KB و پیشنهادهای مبتنی بر شواهد را نمایش می‌دهد.
- سناریوهای مرحله‌ای Helpdesk را از فایل JSON قابل انتقال می‌خواند و مدیریت می‌کند.
- اجرای سناریو و تولید متن قابل کپی برای CRM یا ارجاع به L2 را پشتیبانی می‌کند.
- هیچ داده‌ای را در CRM ثبت یا تغییر نمی‌دهد.
- احراز هویت سازمانی Production، RBAC Production، Audit کامل و ثبت نهایی در CRM هنوز پیاده‌سازی نشده‌اند.

هدف فعلی پروژه، ایجاد یک ابزار عملیاتی Read-Only برای بررسی جریان کار و Smart Troubleshooting است؛ نه جایگزینی CRM و نه خودکارسازی تصمیم نهایی.

### قابلیت جدید برای بررسی دقیق

در نسخه فعلی، بخش «متعلقات مورد» به Timeline زمانی تبدیل شده است. Note ارتباطی، Post داخلی و Task داخلی L2 در یک فهرست ترکیبی از جدیدترین به قدیمی‌ترین نمایش داده می‌شوند و هر رویداد شامل نوع فعالیت، تاریخ و ساعت، عنوان/متن و نام ثبت‌کننده است. شناسه و نام ثبت‌کننده از فیلدهای واکشی‌شده CRM و مقدار قالب‌بندی‌شده OData خوانده می‌شود؛ در صورت نبود شواهد، رابط عبارت صریح «نام ثبت‌کننده در داده CRM موجود نیست» را نشان می‌دهد و هویت را حدس نمی‌زند. مدل بررسی‌کننده باید صحت این زنجیره را در `crm/client.py`، `crm/local_store.py` و `docs/app/index.html` ارزیابی کند.

## ۲. وضعیت بررسی‌شده مخزن

### ساختار مهم

```text
crm/
  analyzer.py              تحلیل کیفیت و پیشنهادهای مستند به شواهد
  client.py                اتصال REST فقط خواندنی به CRM
  local_store.py           ذخیره Snapshot و بازخورد در SQLite
  scenario_store.py        ذخیره و اعتبارسنجی سناریوها در JSON

scripts/
  local_app.py             سرور HTTP محلی و API برنامه
  sync_crm_to_local.py     همگام‌سازی CRM به SQLite
  crm_readonly_probe.py    بررسی اتصال Read-Only به Entityها
  crm_views_probe.py       بررسی Viewهای CRM

docs/app/
  app-shell.html           داشبورد اصلی
  index.html               صفحه بازبینی موارد و Copilot
  settings.html            تنظیم View و واکشی Snapshot
  scenarios.html           اجرای سناریوها
  scenario-management.html مدیریت و ویرایش سناریوها
  scenario-checklist.html اجرای چک‌لیست مرحله‌ای

config/
  scenarios.json           سناریوهای قابل انتقال
  settings.example.env     نمونه تنظیمات بدون Secret
  version-history.json     تاریخچه نگارش‌ها

data/
  pargar-support.sqlite3   Snapshot محلی؛ در زمان اجرا ایجاد/به‌روزرسانی می‌شود

docs/api/openapi.yaml      قرارداد API مستندشده
migrations/                مرجع اولیه ساختار داده
tests/                     تست‌های فعلی منطق تحلیل و ذخیره‌سازی
run-app.bat                راه‌انداز اصلی برنامه
run-release-0.ps1          نصب وابستگی، همگام‌سازی، اجرای سرور و بازکردن مرورگر
```

## ۳. قابلیت‌های واقعاً موجود

### ۳.۱ اتصال CRM

فایل اصلی: `crm/client.py`

قابلیت‌های موجود:

- اتصال به `https://crm.baridsoft.ir/Main/api/data/v9.0`
- استفاده از Windows Integrated Authentication/Negotiate
- خواندن `WhoAmI`
- خواندن Case از Entity `incidents`
- خواندن Note از `annotations`
- خواندن Task از `tasks`
- خواندن Post از مسیر مربوط به Case
- خواندن Knowledge Base از `knowledgearticles`
- خواندن Viewهای سازمانی و شخصی از `savedqueries` و `userqueries`
- اجرای FetchXML View انتخاب‌شده برای واکشی Caseها
- خواندن جزئیات کامل Case با `get_case_context`
- تکمیل اطلاعات View با جزئیات کامل Case در زمان Snapshot

محدودیت مهم:

- Client فعلی فقط عملیات GET/Read-Only را ارائه می‌کند.
- عملیات Create، Update، Delete، تغییر مالک، تغییر وضعیت، ثبت Note یا ثبت نتیجه در CRM وجود ندارد.

### ۳.۲ Snapshot داخلی

فایل اصلی: `crm/local_store.py`

SQLite برای ذخیره این موارد استفاده می‌شود:

- Case
- Note مرتبط با Case
- Task مرتبط با Case
- Post مرتبط با Case
- Knowledge Article
- بازخورد محلی کاربر
- اجرای همگام‌سازی
- محدوده Snapshot شامل View فعال CRM

Snapshot هنگام واکشی مجدد جایگزین می‌شود و اطلاعات CRM در آن به‌صورت محلی نگهداری می‌گردد.

### ۳.۳ محدوده View و مشاهده موارد

در نسخه Working Tree، فیلتر مالک مستقیم کاربر حذف شده و موارد از View انتخاب‌شده CRM خوانده می‌شوند. قبل از نمایش Snapshot:

- هویت کاربر با `WhoAmI` بررسی می‌شود.
- View ذخیره‌شده با فهرست Viewهای قابل‌دسترسی در CRM تطبیق داده می‌شود.
- فقط Snapshot مربوط به View مجاز نمایش داده می‌شود.
- همه موارد موجود در همان View قابل جست‌وجو و بازبینی هستند.

این تصمیم برای نقش مدیر و کارشناسان Helpdesk مناسب‌تر از محدودکردن به مالک مستقیم Case است، اما مدل بررسی‌کننده باید بررسی کند آیا کنترل دسترسی View در CRM برای نیاز امنیتی سازمان کافی است یا خیر.

### ۳.۴ صفحه بازبینی موارد

فایل: `docs/app/index.html`

قابلیت‌های موجود:

- جست‌وجوی مورد بر اساس شماره، عنوان، شرح، خدمت و دسته‌بندی
- نمایش نتایج به‌صورت کارت قابل انتخاب
- نمایش اطلاعات مورد انتخاب‌شده
- نمایش وضعیت، خدمت، دسته‌بندی، عنوان و شرح
- نمایش Noteهای ارتباطی
- نمایش Postهای داخلی
- نمایش Taskهای داخلی L2
- نمایش Copilot متناسب با مورد انتخاب‌شده
- نمایش کمبودهای اطلاعاتی
- پیشنهاد سؤال‌های تکمیلی
- پیشنهاد مقاله مرتبط از KB با امتیاز هم‌پوشانی واژگان
- نمایش دلیل، سطح اتکا و شواهد پیشنهاد
- تولید پیش‌نویس پاسخ/Note محلی
- ثبت پذیرش، ویرایش یا رد پیشنهاد در SQLite داخلی
- اجرای سناریوی مرتبط برای مورد انتخاب‌شده
- نمایش جزئیات مورد در پنجره جمع‌شونده
- نمایش «موارد نیازمند تکمیل» زیر پنجره جزئیات

### ۳.۵ تحلیل و پیشنهاد

فایل: `crm/analyzer.py`

منطق فعلی شامل این موارد است:

- کنترل عنوان و شرح
- بررسی وجود نشانه‌هایی از نسخه محصول
- بررسی محیط اجرا
- بررسی اقدام، نتیجه، حل یا راهنمایی
- تشخیص فیلدهای کمبوددار
- تولید سؤال‌های تکمیلی
- جست‌وجوی KB بر اساس هم‌پوشانی واژه‌های Case با عنوان و محتوای مقاله
- جلوگیری از پیشنهاد مقاله در نبود شواهد کافی
- تولید متن پیش‌نویس با سطح اتکا و مبنای تحلیل
- تولید پیشنهادهای عملیاتی با مالک پیشنهادی مانند L1 یا L2

این منطق در حال حاضر موتور معنایی، Embedding، جست‌وجوی برداری یا مدل زبانی بیرونی ندارد؛ رتبه‌بندی فعلی عمدتاً واژه‌محور و Rule-Based است.

## ۴. APIهای موجود

فایل اجرایی API: `scripts/local_app.py`

| مسیر | روش | وضعیت و کاربرد |
|---|---|---|
| `/` | GET | ورود به `portal.html` |
| `/api/app-info` | GET | نسخه API و Read-Only بودن |
| `/api/views` | GET | فهرست Viewهای Case از CRM |
| `/api/load-view` | POST | واکشی View و ساخت Snapshot محلی؛ فقط خواندن از CRM |
| `/api/cases` | GET | فهرست موارد Snapshot مجاز |
| `/api/cases/{caseId}` | GET | جزئیات Case و Timeline مرتبط |
| `/api/cases/{caseId}/analysis` | GET | تحلیل کمبودها، KB و پیشنهادها |
| `/api/scenario-kb?q=...` | GET | جست‌وجوی مقاله در KB محلی |
| `/api/feedback` | POST | ثبت بازخورد محلی؛ بدون CRM Write |
| `/api/scenarios` | GET/PUT | خواندن یا ذخیره سناریوهای JSON محلی |
| `/api/scenarios/export` | GET | خروجی قابل انتقال سناریوها |
| `/api/version-history` | GET | تاریخچه نگارش‌ها |
| `/api/release-0/discovery-summary` | GET | خلاصه مقدماتی Snapshot |

### کنترل‌های API

- محدودیت طول Query
- محدودیت حجم Payload سناریو
- Allowlist برای نوع بازخورد و اقدام
- خطاهای ساختاریافته و پیام فارسی
- Headerهای امنیتی شامل CSP، `nosniff`، `SAMEORIGIN` و `no-referrer`
- عدم ثبت Secret در Log و Frontend

محدودیت مهم: API محلی احراز هویت نشست/کاربر در سطح Production و RBAC کامل ندارد. کنترل فعلی بر مبنای هویت Windows/CRM، مجازبودن View و اجرای محلی است.

## ۵. تجربه کاربری و جریان‌های اصلی

### جریان بازبینی یک مورد

1. اجرای `run-app.bat`
2. ورود به داشبورد یا صفحه بازبینی
3. انتخاب View و واکشی Snapshot در صفحه تنظیمات
4. ورود به صفحه بازبینی موارد
5. جست‌وجوی شماره یا عنوان مورد
6. انتخاب یک مورد
7. مشاهده اطلاعات کامل در پنجره جمع‌شونده
8. مشاهده کمبودهای اطلاعاتی زیر همان پنجره
9. بررسی Note، Post، Task و مقالات KB در Copilot
10. پذیرش، اصلاح یا رد پیشنهاد در سطح محلی
11. اجرای سناریوی مرحله‌ای در صورت نیاز
12. کپی متن خروجی برای ثبت دستی در CRM یا ارسال به L2

### جریان Smart Troubleshooting

1. انتخاب سناریو
2. مشاهده مرحله جاری
3. انتخاب پاسخ آماده یا ثبت پاسخ کارشناس
4. ثبت شواهد و نتیجه مرحله
5. جست‌وجوی KB برای همان مرحله
6. ادامه تا پایان سناریو
7. تولید متن خلاصه قابل کپی

### Human-in-the-Loop

Copilot فقط پیشنهاد، هشدار، سؤال تکمیلی، پیش‌نویس و خلاصه تولید می‌کند. تصمیم نهایی، ویرایش، ارسال و ثبت رسمی بر عهده کارشناس مجاز است.

## ۷. امنیت، حریم خصوصی و محدودیت‌های عملیاتی

### کنترل‌های موجود

- عدم وجود عملیات Write در Adapter CRM
- استفاده از حساب Windows به‌جای قراردادن رمز عبور در کد
- عدم نمایش Secret در Frontend
- Headerهای امنیتی پایه
- محدودسازی ورودی‌ها
- Allowlist برای انواع بازخورد
- محدودیت حجم سناریو
- بررسی مجازبودن View Snapshot قبل از نمایش

### کنترل‌های تکمیل‌نشده

- احراز هویت کاربر در سطح Web Application
- RBAC Production مستقل از CRM
- مدیریت نشست و CSRF کامل
- Audit Log ساختاریافته و غیرقابل‌دستکاری
- TLS/HTTPS برای سرویس محلی یا استقرار سازمانی
- رمزنگاری داده SQLite در حالت سکون
- سیاست نگهداری و حذف داده Snapshot
- تفکیک دسترسی مدیر، L1 و L2 در UI/API
- کنترل ضمیمه، فایل و داده‌های حساس
- Rate Limit و کنترل هم‌زمانی API
- Backup/Restore عملیاتی

### ریسک‌های مهم

1. Snapshot محلی شامل داده CRM و احتمالاً اطلاعات حساس است.
2. همه کاربران سیستم‌عامل دارای دسترسی به فایل Snapshot ممکن است بتوانند داده را بخوانند.
3. ثبت بازخورد محلی به‌تنهایی Audit سازمانی محسوب نمی‌شود.
4. منطق رتبه‌بندی KB واژه‌محور است و ممکن است رابطه معنایی ضعیف یا نادرست بدهد.
5. بدون Pagination کامل، Viewهای حجیم ممکن است زمان واکشی و حافظه زیادی مصرف کنند.
6. جزئیات کامل هر Case با درخواست جداگانه خوانده می‌شود و در Viewهای بزرگ به N+1 Request تبدیل می‌شود.
7. مدل فعلی هنوز برای چند کاربر هم‌زمان و استقرار مرکزی طراحی نشده است.

## ۸. کیفیت و تست فعلی

- تست N+1 واکشی جزئیات
- تست UI مرورگر و انتخاب مورد
- تست سناریو از ایجاد تا خروجی نهایی
- تست هم‌زمانی و چند کاربر
- تست Backup/Restore
- تست امنیتی جامع مطابق OWASP ASVS

## ۹. مغایرت‌ها و نکات قابل توجه برای بررسی‌کننده

مدل AI باید موارد زیر را به‌صورت جداگانه بررسی کند:

1. README قدیمی‌تر از کد فعلی است و هنوز برخی بخش‌ها را «نمونه نمایشی» یا فاقد View واقعی توصیف می‌کند.
2. مستندات Release 0، Release 1 و Release 2 هم‌زمان در مخزن وجود دارند؛ باید مشخص شود کدام قابلیت واقعاً در Scope فعلی است.
3. نام‌گذاری API و UI در بعضی مستندات هنوز `Case` انگلیسی است، در حالی که UI جدید از «مورد» استفاده می‌کند.
4. OpenAPI باید با Endpointهای جدید مانند `/api/app-info` و رفتار View Scope تطبیق داده شود.
5. `settings.html` در Working Tree ایجاد شده اما ممکن است در آخرین Commit GitHub نباشد.
6. فایل‌های تغییرکرده Working Tree هنوز نشان‌دهنده وضعیت نهایی GitHub نیستند.
7. مسیر اجرای سناریو، مدیریت سناریو و API ذخیره‌سازی JSON باید از نظر مجوز و اعتبارسنجی مستقل بررسی شود.
8. وضعیت «مدیر همه موارد را می‌بیند» در طراحی فعلی به View مجاز CRM وابسته است، نه نقش مدیر مستقل در برنامه.
9. Task، Post و Note از نظر معنای کسب‌وکار در مستندات باید با تیم Helpdesk نهایی تطبیق داده شوند.
10. مفهوم «مقاله مرتبط» فعلاً بر هم‌پوشانی واژگان است و نباید به‌عنوان تطبیق معنایی قطعی معرفی شود.

## ۱۰. پرسش‌های مشخص از مدل AI

لطفاً پاسخ خود را در بخش‌های زیر ارائه کن:

### الف) ارزیابی معماری

- آیا جداسازی CRM Adapter، Snapshot، Analyzer، API و UI مناسب است؟
- مهم‌ترین بدهی معماری چیست؟
- برای تبدیل این ابزار محلی به سرویس سازمانی چندکاربره چه تغییراتی لازم است؟

### ب) ارزیابی امنیت

- آیا مدل «احراز هویت Windows + View مجاز CRM + Snapshot محلی» کافی است؟
- چه مسیرهایی برای افشای داده وجود دارد؟
- اولویت پیاده‌سازی Authentication، RBAC، Audit، Encryption و CSRF چیست؟
- آیا Snapshot SQLite باید حذف، رمزنگاری یا محدود به سرور مرکزی شود؟

### ج) ارزیابی صحت داده

- آیا تکمیل جزئیات Case از Endpoint جداگانه بعد از واکشی View قابل اتکا است؟
- ریسک‌های N+1 Request چیست؟
- چه فیلدهایی برای Case، Note، Task، Post و KB باید اجباری شوند؟
- چطور باید اختلاف View، Snapshot و CRM زنده گزارش شود؟

### د) ارزیابی Copilot و KB

- آیا روش رتبه‌بندی واژه‌محور برای Pilot مناسب است؟
- چه معیارهایی برای سنجش Precision، Recall و Groundedness لازم است؟
- چه زمانی استفاده از جست‌وجوی Hybrid یا Embedding منطقی می‌شود؟
- چطور باید پیشنهاد حدسی از پیشنهاد مستند جدا شود؟

### هـ) ارزیابی تجربه کاربری

- آیا جریان انتخاب View در صفحه تنظیمات و بازبینی مورد در صفحه جدا مناسب است؟
- آیا آکاردئون اطلاعات مورد و نمایش کمبودها در زیر آن برای کارشناس قابل فهم است؟
- مهم‌ترین اصلاح UX برای استفاده روزانه Helpdesk چیست؟

### و) ارزیابی Smart Troubleshooting

- آیا مدل سناریو برای پاسخ تک‌انتخابی، چندانتخابی، فیلد اجباری و شاهد کافی است؟
- آیا خروجی قابل کپی برای L2/CRM اطلاعات لازم را دارد؟
- چه داده‌هایی باید برای ارزیابی Pilot ثبت شود؟

### ز) اولویت‌بندی

یک Backlog اولویت‌بندی‌شده ارائه کن:

- سه اقدام فوری با اثر زیاد و ریسک کم
- سه اقدام لازم پیش از Pilot واقعی
- سه اقدام لازم پیش از Production
- مواردی که فعلاً نباید ساخته شوند

### ح) تصمیم Go / No-Go

در پایان، یکی از این گزینه‌ها را انتخاب کن و دلیل بده:

- آماده Pilot محدود Read-Only
- نیازمند اصلاح قبل از Pilot
- مناسب Demo، اما نامناسب Pilot
- نیازمند بازطراحی معماری

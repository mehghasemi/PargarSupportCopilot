# بررسی MyBarid-AI برای اتصال Pargar Support Copilot به CRM

**تاریخ بررسی:** ۲۹ اوت ۲۰۲۶  
**دامنه بررسی:** فقط تحلیل کد موجود و استخراج الگوی قابل استفاده؛ بدون اتصال به CRM و بدون تغییر در مخزن مرجع

## نتیجه اصلی

پروژه `MyBarid-AI` از مسیر **Viewهای CRM و Export آن‌ها** با داده CRM کار می‌کند. در نسخه بررسی‌شده، این مسیر به‌صورت خواندن فایل Excel خروجی View پیاده‌سازی شده است؛ یعنی برنامه مستقیماً با API/Dataverse احراز هویت نمی‌کند، بلکه کاربر View موردنظر را در CRM باز می‌کند، Export می‌گیرد و فایل را به برنامه می‌دهد.

پس عبارت دقیق‌تر این است: **در MyBarid-AI اتصال مستقیم API به CRM در کد فعلی دیده نشد؛ اما در Pargar Support Copilot یک Adapter مستقل REST/Read-Only پیاده‌سازی و با CRM سازمانی آزمایش شده است.**

مسیر داده آن به این شکل است:

```text
Export از Dynamics CRM (Excel Notes/Tasks)
        ↓
loader → mapper → validator → cleaner
        ↓
pipeline / rule engine / اختیاری AI
        ↓
گزارش و داشبورد
```

بنابراین از آن پروژه می‌توان الگوی مدل داده، Mapping، اعتبارسنجی، اتصال Task به Case، Timeline و لایه Bridge را گرفت. همچنین الگوی ورود داده از Viewهای Exportشده برای شروع کار Pargar قابل استفاده است؛ اما کد آماده‌ای برای ورود خودکار به CRM یا خواندن مستقیم View از API در آن وجود ندارد.

## بخش‌های قابل استفاده به‌عنوان الگو

### 1. مدل داده کانونی

در `data/validator.py`، رکوردهای `NoteRecord` و `TaskRecord` فیلدهای کانونی دارند و به نام ستون Export وابسته نیستند. این ایده برای Pargar Support Copilot مناسب است:

- تعریف مدل داخلی مستقل از نام فیلدهای CRM
- جداسازی داده خام از داده نرمال‌شده
- امکان جایگزینی منبع Excel با منبع CRM بدون تغییر لایه‌های بالاتر

### 2. Mapping و کنترل کیفیت

در `data/mapper.py`، نام‌های احتمالی ستون‌ها به فیلدهای کانونی نگاشت می‌شوند و موارد زیر گزارش می‌شوند:

- فیلدهای الزامیِ پیدا‌نشده
- ستون‌های مبهم
- ستون‌های بدون استفاده
- هشدارهای Mapping

در اتصال مستقیم، همین مفهوم باید برای نام فیلدهای View یا پاسخ API حفظ شود؛ یعنی View CRM نباید مستقیماً به UI وابسته شود.

### 3. اتصال Task به Case

پروژه قبلی ابتدا از شماره Case و در نبود آن از تطبیق متنی `Regarding` و عنوان Case استفاده می‌کند. این برای تحلیل تاریخی مفید است، اما برای اتصال مستقیم CRM باید اولویت با شناسه واقعی رابطه باشد و تطبیق متنی فقط به‌عنوان حالت احتیاطی و دارای هشدار باقی بماند.

### 4. لایه Bridge

در `bridge.py`، UI از طریق یک API پایتون به عملیات برنامه دسترسی دارد. برای Pargar Support Copilot می‌توان همین جداسازی را نگه داشت:

```text
UI Copilot
   ↓
Bridge / Application Service
   ↓
CRM Read Adapter
   ↓
Dynamics CRM / Dataverse
```

### 5. امنیت تنظیمات

پروژه قبلی کلید API را در Windows DPAPI نگهداری می‌کند و در Export تنظیمات، کلید را منتقل نمی‌کند. این الگو برای Credentialهای CRM نیز کافی به‌نظر نمی‌رسد مگر اینکه روش احراز هویت سازمانی و سیاست امنیتی CRM مشخص شود؛ بنابراین Credential نباید در فایل تنظیمات یا مخزن ذخیره شود.

## تفاوت مهم با نیاز Pargar Support Copilot

پروژه قبلی برای خواندن خروجی Viewهای CRM طراحی شده است؛ بنابراین آن مسیر همچنان به‌عنوان الگوی Import کنترل‌شده قابل استفاده است. در Pargar، علاوه بر آن، مسیر خواندن زنده REST نیز به‌صورت مستقل ایجاد شده است. این دو مسیر با هم تفاوت دارند:

- **مسیر موجود و قابل استفاده:** کاربر View را در CRM انتخاب و Export می‌کند؛ Pargar فایل خروجی را می‌خواند.
- **مسیر موجود در Pargar:** Adapter خواندنی REST برای Case، Note، Task، Knowledge Base و فهرست Viewهای ذخیره‌شده.

هر دو منبع باید خروجی خود را به مدل داخلی مشترک تبدیل کنند تا طراحی UI و منطق Copilot با تغییر منبع داده به‌هم نریزد.

## معماری اجرایی فعلی در Release 0

```text
CRM REST Reader (Read-Only)
        │
        ├── Case Mapper
        ├── Related Activities Reader (Note/Task)
        └── KB Reader
                ↓
        Canonical Case Context
                ↓
        Completeness Checker
        Knowledge Retriever
        Draft Note Generator
                ↓
        Copilot UI
```

قواعد لازم:

1. Reader فقط Viewهای مشخص و فیلدهای لازم را بخواند.
2. هیچ مسیر نوشتن در Adapter اولیه وجود نداشته باشد.
3. داده خام CRM مستقیماً به Prompt یا UI فرستاده نشود؛ ابتدا حداقل‌سازی و نرمال‌سازی شود.
4. هر پیشنهاد شامل منبع، دلیل، سطح اتکا و هشدار باشد.
5. نبود دسترسی یا خطای CRM باید با حالت «ادامه کار بدون Copilot» مدیریت شود.
6. اطلاعات مشتری، ضمائم و فیلدهای حساس پیش‌فرض خوانده نشوند.
7. Viewهای CRM قرارداد داده‌اند؛ تغییر View باید قابل تشخیص و گزارش باشد.

## پیشنهاد مسیر بدون به‌هم‌زدن طراحی

Prototype مفهومی موجود حفظ شود. برای تست با داده واقعی، Provider مستقیم CRM در کنار Provider نمایشی قرار می‌گیرد؛ بدون دسترسی نوشتن و بدون تغییر جریان Copilot:

```text
DemoDataProvider  ─┐
                   ├─ Canonical Case Context ── Copilot UI
ExcelExportProvider┤
CRMRestProvider  ──┘
```

به این ترتیب، ظاهر و جریان کار برنامه با تغییر منبع داده دوباره طراحی نمی‌شود. Provider نمایشی حفظ می‌شود و Provider CRM مستقیم فعلاً فقط برای خواندن و Probe/Discovery استفاده می‌شود.

## مواردی که هنوز برای استفاده عملیاتی از اتصال مشخص نیست

- نام و شناسه Viewهای نهایی موردنظر برای Pilot
- موجودیت و فیلدهای واقعی Case، Note، Task و KB
- امکان خواندن رابطه‌های مرتبط از View/API
- سیاست انتقال داده به سرویس AI
- روش Audit و ثبت رخداد دسترسی

این موارد برای انتخاب View و تعریف داده Pilot باید تأیید شوند؛ اتصال فعلی فقط GET/Read-Only است و به‌تنهایی به معنی مجوز اجرای Pilot روی داده زنده نیست.

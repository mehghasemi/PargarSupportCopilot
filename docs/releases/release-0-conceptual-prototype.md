# نمونه مفهومی قابل‌مشاهده — Release 0

**وضعیت:** طراحی مفهومی، بدون اتصال واقعی  
**هدف:** نشان‌دادن شکل کار برنامه و تجربه کارشناس با داده ساختگی  
**خارج از تعهد:** این سند طراحی فنی، مجوز دسترسی یا برنامه اجرای Pilot واقعی نیست.

## 1) تصویر کلی برنامه

Copilot در کنار صفحه Case قرار می‌گیرد و سه کار انجام می‌دهد:

1. اطلاعات Case را بررسی و کمبودهای مهم را یادآوری می‌کند.
2. بر اساس متن و زمینه Case، منابع دانش معتبر را پیشنهاد می‌دهد.
3. نتیجه تعامل را به شکل پیش‌نویس Note آماده می‌کند.

کارشناس همچنان تصمیم‌گیرنده است. Copilot هیچ پاسخ، Note، وضعیت، مالک یا ارجاعی را به‌صورت خودکار در CRM ثبت نمی‌کند.

```text
┌────────────────────────────── صفحه Case ──────────────────────────────┐
│ اطلاعات Case                  │ پنل Pargar Support Copilot             │
│                              │                                         │
│ Title                        │ وضعیت Case: نیازمند تکمیل              │
│ Description                  │ ۳ مورد مهم برای بررسی                   │
│ Case Service                 │                                         │
│ Category / Subcategory       │ پیشنهادهای KB                           │
│ Status / Owner               │ [مقاله ۱] [مقاله ۲] [مقاله ۳]           │
│                              │                                         │
│ Note و فعالیت‌ها             │ پیش‌نویس Note                           │
│                              │ [مشاهده] [ویرایش] [پذیرش برای ثبت]      │
└──────────────────────────────┴─────────────────────────────────────────┘
```

## 2) جریان کار مفهومی کارشناس

1. کارشناس یک Case نمونه را باز می‌کند.
2. Copilot متن و فیلدهای مجاز Case را تحلیل می‌کند.
3. وضعیت کامل‌بودن Case و کمبودهای مشخص نمایش داده می‌شود.
4. کارشناس اطلاعات لازم را تکمیل یا پیشنهاد Copilot را رد می‌کند.
5. Copilot حداکثر سه مقاله KB تأییدشده را با منبع و میزان اتکا نشان می‌دهد.
6. کارشناس مقاله را می‌بیند و در صورت نیاز متن Case را اصلاح می‌کند.
7. Copilot یک پیش‌نویس Note از اطلاعات و اقدام‌های ثبت‌شده آماده می‌کند.
8. کارشناس پیش‌نویس را بازبینی می‌کند؛ ثبت نهایی فقط با تأیید او انجام می‌شود.

## 3) نمونه Case ساختگی

```text
Case Service: ۱۵ - راهنمایی
Title: راهنمای تنظیم گزارش فروش در پایان ماه
Description:
  مشتری درباره نحوه تنظیم گزارش فروش سؤال دارد، اما نام ماژول،
  نسخه محصول و نتیجه اقدام انجام‌شده در متن ثبت نشده است.
Category: گزارش‌گیری
Subcategory: نیازمند بررسی
Status: در حال بررسی
```

### نمایش پیشنهادی Copilot

**وضعیت ثبت Case: نیازمند تکمیل**

| مورد | وضعیت | پیشنهاد |
|---|---|---|
| عنوان | قابل‌فهم | بدون تغییر |
| شرح مسئله | ناقص | مشخص‌کردن ماژول و هدف گزارش |
| نسخه محصول | ثبت نشده | پرسش از مشتری یا کارشناس |
| نتیجه اقدام | ثبت نشده | ثبت اقدام انجام‌شده، در صورت وجود |
| طبقه‌بندی | موقت | انتخاب Subcategory مناسب یا «سایر» |

**سؤال‌های تکمیلی پیشنهادی:**

- گزارش برای کدام ماژول و کدام نوع کاربر است؟
- نسخه محصول و محیط استفاده چیست؟
- آیا کارشناس قبلاً اقدامی انجام داده است؟ نتیجه چه بوده؟

**پیشنهادهای دانش:**

1. «راهنمای تنظیم گزارش فروش» — منبع: KB تأییدشده — اتکا: بالا
2. «پارامترهای گزارش پایان ماه» — منبع: KB تأییدشده — اتکا: متوسط

اگر مقاله مرتبط تأییدشده‌ای پیدا نشود، Copilot باید صریحاً بنویسد: «مقاله معتبر پیدا نشد»؛ نباید از Notes یا Case تاریخی پاسخ قطعی بسازد.

## 4) رفتار پیشنهادها و تصمیم کارشناس

هر پیشنهاد باید این اطلاعات را نمایش دهد:

- نوع پیشنهاد: کمبود اطلاعات، سؤال تکمیلی، مقاله یا پیش‌نویس
- منبع
- دلیل پیشنهاد
- میزان اتکا: بالا، متوسط یا پایین
- محدودیت یا هشدار
- وضعیت تعامل: پذیرفته‌شده، پذیرفته‌شده با ویرایش یا ردشده

نمونه:

```text
پیشنهاد: افزودن نسخه محصول
دلیل: برای بررسی ارتباط مقاله با Case لازم است.
منبع: فیلد نسخه در Case خالی است.
اتکا: بالا
اقدام کارشناس: [پذیرش] [ویرایش] [رد]
```

## 5) پیش‌نویس Note

پیش‌نویس فقط از اطلاعات مشاهده‌شده و اقدام‌های ثبت‌شده ساخته می‌شود:

```text
خلاصه مسئله:
مشتری درباره تنظیم گزارش فروش پایان ماه راهنمایی درخواست کرده است.

اطلاعات تکمیل‌شده:
- ماژول: ................................
- نسخه: ................................
- محیط: ................................

اقدام/راهنمایی ارائه‌شده:
بررسی مقاله «راهنمای تنظیم گزارش فروش» از KB تأییدشده.

وضعیت:
پیش‌نویس — نیازمند بازبینی و تأیید کارشناس
```

دکمه «ثبت نهایی» باید از «ذخیره پیش‌نویس» متمایز باشد. در نمونه مفهومی، هیچ‌کدام به CRM واقعی متصل نیستند.

## 6) حالت‌های اصلی صفحه

| حالت | رفتار مورد انتظار |
|---|---|
| اطلاعات کافی نیست | فهرست کوتاه کمبودها و سؤال‌های تکمیلی نمایش داده شود |
| اطلاعات کافی است | خلاصه وضعیت و پیشنهادهای مرتبط نمایش داده شود |
| KB معتبر موجود است | فقط مقالات تأییدشده با منبع و وضعیت تأیید نمایش داده شوند |
| KB معتبر موجود نیست | نبود منبع معتبر صریح اعلام شود؛ پاسخ قطعی ارائه نشود |
| پیشنهاد نامرتبط است | کارشناس بتواند آن را رد و دلیل را ثبت کند |
| خطا یا عدم دسترسی | برنامه خطا را شفاف نشان دهد و کارشناس بتواند بدون Copilot ادامه دهد |

## 7) مرزهای ایمنی در طراحی مفهومی

- Copilot پاسخ را برای مشتری ارسال نمی‌کند.
- Copilot Note، Status، مالک Case یا ارجاع را نهایی نمی‌کند.
- پیشنهاد مبتنی بر Case، Note یا Task تاریخی با برچسب «شواهد تاریخی / نیازمند بررسی» نمایش داده می‌شود.
- اعلام قطعی Bug، اجرای تغییر فنی و انتشار KB در این طراحی وجود ندارد.
- داده نمونه این سند ساختگی است و نباید با داده واقعی مشتری جایگزین شود.

## 8) معیار بازبینی این نمونه مفهومی

این نمونه زمانی قابل قبول است که مدیر یا کارشناس بتواند بدون اتصال واقعی پاسخ دهد:

1. آیا محل نمایش اطلاعات و پیشنهادها قابل فهم است؟
2. آیا ترتیب کار با جریان فعلی Helpdesk سازگار به نظر می‌رسد؟
3. آیا مرز پیشنهاد Copilot و تصمیم کارشناس روشن است؟
4. آیا پیش‌نویس Note برای بازبینی انسانی قابل استفاده است؟
5. کدام بخش در نگاه اول مبهم، اضافه یا مزاحم است؟

پاسخ به این موارد فقط برای اصلاح همین طراحی مفهومی استفاده می‌شود و به‌تنهایی مجوز اجرای Pilot واقعی نیست.

## 9) فایل نمایشی قابل اجرا

نسخه تعاملی عملیاتی در [`../app/index.html`](../app/index.html) قرار دارد. مسیر اصلی استفاده، اجرای سرور محلی و بازکردن مرکز برنامه است؛ داده‌ها از CRM با دسترسی فقط‌خواندنی واکشی می‌شوند.
